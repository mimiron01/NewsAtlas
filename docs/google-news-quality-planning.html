NewsAtlas — Google News Feed Quality Planning

What can technically be improved in the Google News RSS ingestion path so the signals it produces actually fit — a code-grounded audit plus a phased implementation plan

Status: Planning (2026-07-30). Research and design only — no code has been written for this doc.
Reported symptom (this conversation): too much irrelevant noise. Articles arrive that aren't really about the target company, or have no business angle. This is a precision complaint, and the phase ordering below reflects that.
Builds on: news-source-expansion-planning.html §7.2/§15 (the original GoogleNewsRSSClient spec and its open questions), v1-release-roadmap.html §2.3 (query tightening + source allowlists, already shipped), ingestion-reliability-planning.html §5 (the wrong-company attribution root cause and its grounding fix), theme-search-planning.html §3/§5/§6 (the theme path, which shares this client)
Codebase grounded against: commit d5233ad on main. Everything described as "current state" was read in the tree at that commit, with file:line references.
Verification caveat: the research environment has no outbound egress to news.google.com (the agent proxy denies CONNECT), so no claim below was tested against the live feed. Behavioural claims about Google's query syntax come from external documentation (see §4) and are flagged verify where a spike must confirm them before implementation depends on them.

1. Decisions already made

Resolved in the planning conversation on 2026-07-30, recorded so an implementation session doesn't re-litigate them:

Decision — the problem to optimize for is precision, not recall. The complaint is noise: articles that aren't really about the target company, or that are but carry no business angle. Where a change trades recall for precision, take it; where the two conflict, precision wins. (This is the opposite trade-off from what a "we're missing news" complaint would justify, so it is recorded explicitly.)
Decision — the primary market is German (DE:de), and target companies get their own edition override. TargetCompany gains google_news_country/google_news_language with the same NULL-means-inherit semantics ThemeWatch already has (models/theme_watch.py:36-37). A single workspace-wide edition can only ever be right for one market.
Decision — the backend may make outbound requests to publisher domains, behind an admin toggle, off by default. This unlocks resolving Google's redirect links to canonical publisher URLs and pulling a real snippet for articles that today are headline-only. It requires an SSRF-safe fetcher with strict timeouts and a per-run budget (§13).
Decision — the target-company term model is split into distinct roles. Today's single keywords list is doing two incompatible jobs at once (identity alias vs. topic narrower). It becomes aliases (identity), context_terms (narrowing), and exclusion_terms (negation). Migrations and UI changes are acceptable.
Decision — article URLs are deduplicated per company. A story naming two tracked companies must produce a signal for both, so articles.url becomes unique on (target_company_id, url) and the pre-insert check becomes company-scoped. Full consequences in §8.3.
Decision — the workspace source allowlist is a default, not a floor. An entity (company or theme) that sets its own allowlist replaces the workspace list rather than extending it. This supersedes the "union, not override" decision recorded in v1 roadmap §2.3, for the reasons in §7.6. Denylists keep union semantics — the asymmetry is deliberate and explained there.
Decision — the blast radius stays inside the Google News path. Following the precedent set by v1 roadmap §2.3, build_or_query() and the NewsAPI.org / NewsData.io clients are not touched. Where the new term fields must reach those providers and the AI prompts, they do so through a synchronized legacy keywords column (§7.2), not by rewriting those call sites.

3. Findings, ranked

Ranked by expected effect on the reported symptom, with the cheapest fixes first within each tier.

3.1 Tier 1 — precision

F1 — one keywords field is doing two incompatible jobs. build_google_news_query() treats keywords as required topic narrowers (name AND (kw1 OR …)), while article_mentions_company() treats the exact same list as identity aliases (name OR kw1 OR …). Both readings are legitimate, and users have no way to say which they meant. A topic-style keyword ("EV battery") silently hides a funding story about the company; an alias-style keyword can't rescue an article that uses only the alias, because the name is required by the AND. Every other precision lever is capped by this ambiguity.
F2 — the grounding guard is OR while the query is AND. news_query.py:98-116 returns true if any keyword appears, so an article containing only a generic term like "Produktion" and never the company name passes the guard and is stored with that company's target_company_id. This is a live instance of the exact failure class ingestion-reliability §5 was written to close — the guard was added, but with OR semantics that leave the hole open for any company whose keyword list contains a generic term. Fixing F1 fixes this: only identity terms should ever satisfy the guard.
F3 — no exclusion support at all. Google supports -term and -site:. NewsAtlas exposes neither. There is no way to say "not the stock ticker", "not the football club of the same name", or "never msn.com". For a precision complaint this is the most obviously missing tool, and it is cheap: a query-builder change plus two array columns. A denylist is also a better default posture than an allowlist, because site: allowlists cut recall hard while a denylist only removes known-bad sources.
F4 — no per-company edition, and hl is non-canonical. Every company is searched in the workspace edition (ingestion.py:146-152), so a German target in a US:en workspace gets a materially different and worse result set — German-language coverage of a German Mittelstand company largely does not exist in the US/English edition, so what comes back is whatever loosely matched in English. Separately, the client emits hl=de where the documented canonical form is language-region (hl=de-DE); verify whether this changes results in practice.
F5 — the budget cap selects the newest N, not the best N. ingestion.py:429-435 sorts by published_at and truncates. On a syndication-heavy, relevance-ranked feed, "newest" systematically favours aggregator reposts over the original wire story, and spends the whole AI budget on them. A free, deterministic composite score would pick better candidates without a single extra token.

3.2 Tier 2 — yield and freshness

F6 — no time operator in the query. Google News RSS supports when:1h|12h|1d|7d and after:/before:; the builder emits none, and recency is enforced only client-side at google_news_rss_client.py:84. Because the feed is capped at ~100 items with no pagination, the relevance ranking spends that entire budget on all-time-relevant items — external sampling in July 2026 measured a ~6.6-day median item age with only 7.6% of items ≤6h old (§4). With the app's typical 24h lookback, most of every response is fetched, parsed and discarded, and genuinely fresh coverage may never make the 100 at all. Adding when: moves the filter server-side and makes Google re-rank within the window. One-line change, largest yield effect in the document.
F7 — a single compound query per company per run. The feed is free and the limiter permits 20 requests/minute; ingestion uses 1 per company. Two narrower queries (identity-only, identity + context) each get their own 100-item budget and beat one broad compound query on both precision and recall. Worth doing only once Phase 0 can measure whether it helps.
F8 — probable silent query truncation. Google has historically capped queries at roughly 32 words. The validators permit 20 keywords × 100 chars plus 50 allowlist domains (schemas/target_company.py, schemas/settings.py:102); a fully-populated configuration produces a query well past that, and the site: clause is appended last. Whatever Google truncates, it does so silently, and the user sees only "bad results". verify the current limit, then enforce a word budget in the builder with a defined drop order and a visible warning.

3.3 Tier 3 — duplicate work and thin content

F9 — cross-source URL dedupe never fires for Google. Links are news.google.com/rss/articles/CBMi… redirect URLs, not publisher URLs — already acknowledged as a known consequence in news-source-expansion §6/§15. The same story arriving via NewsAPI.org and via Google News is embedded and triaged twice, and only the semantic dedupe (a 0.90 cosine threshold over a 50-item window) can catch it.
F10 — semantic dedupe is weaker for Google than for other sources. The embedding input is title + description (ingestion.py:848), but for Google News the description is a mechanical repeat of the title (models/article.py:70) — so it is effectively a title-only embedding judged against a threshold tuned for title+snippet. A free normalized-title near-duplicate pass before embedding would cut both token cost and duplicate signals.
F11 — every Google article is headline-only. Triage and summarization run on a headline with an explicit "don't expect body text, never quote" directive, so supporting_quote is always empty and confidence is structurally lower for this source. This makes triage's job — the very filter meant to remove noise — much harder than it is for NewsAPI.org snippets.
F12 — global URL uniqueness mis-attributes multi-company stories. Article.url is globally unique (models/article.py) and the pre-insert check at ingestion.py:406 is not company-scoped, so "Acme acquires Beta" produces a signal for whichever company the loop reaches first and silently nothing for the other. Not Google-specific, but Google's syndication depth makes it hit more often.

3.4 Tier 4 — reliability and observability

F13 — self.timeout is set and never used. google_news_rss_client.py:25-28 stores a 10s timeout that nothing reads: feedparser.parse(url) performs its own HTTP request and has no timeout parameter, inheriting the global socket default of None. An unresponsive Google can hang an ingestion run indefinitely. Compare news_client.py:48 and newsdata_client.py:102, which both pass timeout=self.timeout to httpx correctly.
F14 — HTTP status is never checked, so being blocked looks like "no news". A 429/403/consent-page response leaves feed.entries empty; the bozo check at :70 only raises when a parse error is also flagged. A throttled fetch therefore returns an empty list that is indistinguishable from a company genuinely having no coverage — run after run, with nothing in the Logs view. There is also no custom User-Agent (feedparser's default UA is a known throttling magnet) and no retry/backoff.
F15 — the executed query is never persisted and the funnel is invisible. news_source_usage_logs.articles_returned records the count after the client-side date filter; nothing anywhere counts entries dropped by date, by the unsafe-URL guard, by grounding, by URL dedupe, or by the cap. There is no way to answer "why did this company get bad results this run" without attaching a debugger. Every other item in this document is guesswork until this exists — which is why measurement is Phase 0 and not an afterthought.

5. Phase 0 — Measurement

Phase 0 Make the funnel visible before changing it backend + frontend + migration size: S

Nothing else in this plan can be validated without this, and the same instrumentation is what tells you afterwards whether a change helped. It is deliberately small.

0.1 Persist the executed query and the drop funnel

Extend news_source_usage_logs (the existing per-call table, models/news_source_usage_log.py) rather than inventing a parallel one:

ColumnTypeNotes
query_textText, nullableThe q= value actually sent, pre-encoding. Null for providers that don't build one.
articles_rawInteger, default 0Entries the provider returned before any client-side filtering. articles_returned keeps its current post-filter meaning.
drop_countsJSONB, nullable{"stale": 41, "unsafe_url": 0, "not_grounded": 12, "url_duplicate": 6, "over_cap": 22} — one key per pipeline stage that discards a candidate.

The counters are produced by the client (stale, unsafe_url) and by _ingest_target_company (not_grounded, url_duplicate, over_cap), merged into one dict at log time. Cheap: they are loop counters that already exist implicitly as list-length differences.

0.2 A query preview endpoint that spends no AI

POST /admin/news-sources/google-news/preview admin rate-limited — body carries a provisional configuration (name, aliases, context terms, exclusions, allowlist, denylist, country, language, time window) and returns:

{
  "resolved_url": "https://news.google.com/rss/search?q=…",
  "query_text": "\"HWA AG\" (Motorsport OR Rennsport) -Aktie -site:msn.com when:1d",
  "word_count": 9,
  "truncated": false,
  "entries_raw": 100,
  "entries": [
    {"title": "…", "source_name": "Motorsport-Total", "published_at": "…",
     "outcome": "kept" | "stale" | "unsafe_url" | "not_grounded"}
  ]
}

It runs exactly one real fetch (counted by the rate limiter, logged with call_type="preview"), applies the same client-side filters the real path applies, and stops there — no embedding, no triage, no summarization, no writes to articles. This turns every tuning question in this document from an argument into a two-second experiment, and it is the tool an admin uses to curate the term split introduced in Phase 2.

0.3 Surface both in the UI

The recent-activity table in SourcesTab.tsx (already rendering per-call rows) gains an expandable cell showing query_text and the drop breakdown. The preview endpoint gets a "Test query" panel in the same tab, and a "Preview this company's query" button on the target-company edit form in SettingsTargets.tsx.

6. Phase 1 — Fetch, recency, edition

Phase 1 Stop discarding most of what you fetch, and search the right edition backend + frontend + migration size: M

1.1 Own the HTTP request (F13, F14)

Stop letting feedparser do the fetch. Use httpx — which the other two clients already use — and hand the bytes to feedparser for parsing only:

response = httpx.get(
    url,
    timeout=self.timeout,
    headers={"User-Agent": GOOGLE_NEWS_USER_AGENT},
    follow_redirects=True,
)
if response.status_code == 429 or response.status_code >= 500:
    # one bounded retry with backoff, then give up
    ...
if response.status_code != 200:
    raise NewsClientError(
        f"Google News RSS returned HTTP {response.status_code} "
        "(likely throttling — this is not the same as 'no news')"
    )
feed = feedparser.parse(response.content)
Decision — an empty result and a blocked request must never look the same. A non-200 raises NewsClientError, which the provider loop already records per-company into the run's error list (ingestion.py:352-356) and therefore into the Logs view. Today a 429 is silently a zero.

Also: set an explicit descriptive User-Agent, and keep the existing bozo check as a second line of defence for a 200 that isn't valid XML (a consent interstitial, for instance).

1.2 Push recency into the query (F6)

Derive a when: token from the caller's since and append it to every query:

def google_when_operator(since: datetime, now: datetime | None = None) -> str:
    """Smallest Google `when:` bucket that still covers `since`. Google accepts
    hour and day granularities; anything longer than a week is clamped to 7d,
    which is also roughly where the feed's own depth runs out."""
    hours = max(1, ceil((now - since).total_seconds() / 3600))
    if hours <= 1:  return "when:1h"
    if hours <= 12: return "when:12h"
    if hours <= 24: return "when:1d"
    return f"when:{min(ceil(hours / 24), 7)}d"

Gated by a workspace toggle google_news_time_operator_enabled (default on) so it can be switched off without a redeploy if the spike in §15 finds it interacts badly with site: clauses. The client-side since filter stays as a belt-and-braces check — Google's bucket boundaries are coarse and it must not be trusted to be exact.

1.3 Per-company edition, canonical hl (F4)

TargetCompany gains google_news_country/google_news_language (both String(8), nullable, NULL = inherit workspace), mirroring ThemeWatch exactly — including reusing its _normalize_country/_normalize_language validators from schemas/theme_watch.py. _fetch_from_source() passes them through to the existing per-call country/language parameters on fetch_articles() (google_news_rss_client.py:37-39), which already exist for themes — no client signature change needed.

Separately, build hl canonically: hl=de-DE rather than hl=de, by combining language and country when the language has no region subtag. verify

Assumption — the code-level defaults stay US/en. Changing the model defaults would only affect fresh installs while doing nothing for this deployment, and would silently change behaviour for any other. Set DE/de through Settings → News sources instead. Add a validator that rejects implausible country/language pairs outright rather than letting them produce a ceid Google ignores.

1.4 Query word budget (F8)

The builder counts the tokens it emits and, when over budget, drops in a defined, documented order — context terms first, then allowlist domains — never identity terms or exclusions. The truncation is recorded in drop_counts and returned by the preview endpoint as "truncated": true, so silent degradation becomes visible degradation. Budget constant lives next to the builder with the measured limit from the spike.

7. Phase 2 — Query model

Phase 2 Separate identity from topic from exclusion backend + frontend + migration size: L

This is the core precision work (F1, F2, F3) and the largest single change in the plan.

7.1 New term fields

FieldRoleHow it enters the querySatisfies grounding?
aliasesOther ways this company is named ("HWA", "HWA Team")OR'd with the name into the identity groupYes
context_termsTopic narrowers ("Motorsport", "Rennsport")AND'd as an OR-groupNo
exclusion_termsKnown false-positive traps ("Aktie", a same-named football club)-termn/a
google_news_source_denylistDomains to never accept-site:domainn/a

All four exist on TargetCompany; exclusion_terms and google_news_source_denylist also on ThemeWatch and on WorkspaceSettings (workspace denylist unioned into every query, same convention as the allowlist).

7.2 Migration without a behaviour cliff

Decision — the migration copies keywords into context_terms, and leaves aliases empty. That is precisely the role keywords play in today's Google query (name AND (kw…)), so the query is byte-for-byte unchanged on day one and no user has to re-enter anything. The only immediate behaviour change is that the grounding guard gets stricter — it now requires the name (aliases being empty), which is exactly the F2 fix. Curation from there can only improve precision. The tempting alternative — copying keywords into aliases — would loosen the query overnight and make the noise complaint worse.

keywords itself is retained as a derived column, written as aliases + context_terms whenever a company is created or updated, so build_or_query(), the NewsAPI.org/NewsData.io clients, the AI triage/summarize prompts, and the CSV importer all keep working with zero changes (per the §1 blast-radius decision). One synchronization point in the service layer, asserted by a test.

7.3 The new builder

def build_google_news_query(
    *, name, aliases, context_terms, exclusion_terms,
    allow_sites, deny_sites, when=None, require_name_in_title=False,
) -> str:
    identity = _or_group([name, *aliases])                 # ("HWA AG" OR "HWA Team")
    if require_name_in_title:
        identity = _or_group([f"intitle:{t}" for t in ...])
    parts = [identity]
    if context_terms: parts.append(_or_group(context_terms))
    parts += [f"-{t}" for t in _quote_terms(exclusion_terms)]
    if allow_sites:   parts.append(_or_group([f"site:{d}" for d in allow_sites]))
    parts += [f"-site:{d}" for d in deny_sites]
    if when:          parts.append(when)
    return " ".join(parts)
Decision — implicit AND (a space), not the literal token AND. Google's boolean handling is documented as loose rather than strict, a bare space is unambiguously conjunction, and it saves a word against the F8 budget on every query. verify that dropping the literal AND doesn't change result sets, since today's builder emits it.

build_theme_query() gains the same exclusion_terms, deny_sites and when handling; its identity group stays a flat OR of the theme's terms, since a theme has no identity to anchor to (theme-search §3).

7.4 Fix the grounding guard (F2)

def article_mentions_company(*, title, description, full_content, name, aliases) -> bool:
    """Identity terms ONLY. A context term matching is not evidence the article is
    about this company — that conflation is what let keyword-only matches through."""

Call sites in ingestion.py:380-386 pass aliases=target_company.aliases instead of keywords=target_company.keywords. Expect the not_grounded counter from Phase 0 to jump on the first run after this ships — that is the fix working, and Phase 0's instrumentation is what lets you tell that apart from a regression.

7.5 Optional: intitle: and split queries

Two smaller levers, both toggle-gated and both only worth enabling once the preview tool shows they help for a given workspace:

  • Per-company google_news_require_name_in_title (bool, default false) — wraps identity terms in intitle:. Very strong precision lever for generic company names, very costly to recall otherwise.
  • Split queries (F7) — when a company has context terms, issue identity-only and identity+context as two requests and merge by URL. Workspace toggle google_news_query_strategy ∈ {single, split}, default single. Doubles request count (2 of 20/min), zero extra AI cost because the merged set still goes through the Phase 3 scorer and the existing cap.

7.6 Allowlist becomes an overridable default; denylist stays a union

Today both ingestion.py:517 (companies) and :590 (themes) compute union(workspace_allowlist, entity_allowlist), per the "union, not override" decision in v1 roadmap §2.3. That decision is superseded here.

Decision — an entity's own allowlist replaces the workspace allowlist; the workspace list is only the default for entities that don't set one. 
allow_sites = entity.allowlist if entity.allowlist is not None else workspace.allowlist
deny_sites  = workspace.denylist + (entity.denylist or [])   # union, unchanged

Why the union was wrong for allowlists. site: is a hard restriction, not a preference: everything outside the list is excluded outright. Under union, setting a workspace allowlist silently hard-restricts every company and theme in the workspace, and an entity can only ever widen — there is no way to say "this company is covered by trade press the workspace list doesn't include" without also polluting it for everyone else, and no way at all to search a company unrestricted once a workspace list exists. Override makes the workspace list what it reads like in the UI: a sensible default.

Why the union is right for denylists. A denylist subtracts rather than restricts, and "never accept this aggregator" is a workspace-wide policy an individual entity should not be able to silently drop. Union also fails safe: the worst case is slightly less coverage, whereas a dropped denylist entry reintroduces exactly the noise the entry was added to remove. The asymmetry is deliberate and should be stated in the UI help text, not just in code.

Blocker — empty list and "unset" are currently the same value. The allowlist columns are ARRAY(String), nullable=False, default=list, so an entity with no allowlist and an entity that explicitly wants no site restriction are indistinguishable. Override semantics need to tell them apart, or a workspace allowlist becomes impossible to opt out of — the exact problem being fixed.

Fix: make google_news_source_allowlist nullable on target_companies and theme_watches, adopting the NULL-means-inherit convention already established by ThemeWatch.google_news_country/_language (models/theme_watch.py:30-37):

ValueMeaningEffective allowlist
NULLInherit (the default for every entity)Workspace list
[]Explicitly unrestrictedNone — no site: clause at all
["a.com", …]OverrideExactly this list
Decision — the migration backfills the union so no query changes on day one. Set each entity's allowlist to NULL where it is currently empty, and to union(workspace, entity) where it is non-empty. Every effective query is then byte-identical to before the migration, and override semantics govern only what users change afterwards. Without this backfill, every entity with its own list would silently narrow the moment the migration runs — a behaviour change arriving inside what is supposed to be a semantics change.

UI (SettingsTargets.tsx, theme form). The allowlist input needs three visible states, not two: inheriting (showing which workspace domains are in effect, read-only, with an "override" action), overriding (the entity's own tags, with a "revert to workspace default" action), and explicitly unrestricted. Without that, NULL-vs-[] is invisible to the user and the feature is unusable no matter how correct the backend is.

8. Phase 3 — Selection before AI spend

Phase 3 Choose the best N, not the newest N backend size: M

8.1 Composite candidate scoring (F5)

Replace the published_at sort at ingestion.py:429-435 with a deterministic, unit-testable score. No AI, no network, no new dependencies:

SignalWeightRationale
Identity term appears in the title+3Strongest cheap predictor that the article is genuinely about the company.
Identity term appears only in the description+1Weaker but still real.
Domain on the effective allowlist+2The user already said they trust it.
Published within the first half of the lookback window+2Recency, without letting it dominate.
Context term appears anywhere+1Topical fit, as a tiebreak rather than a gate.
Nth (n>3) article from the same domain this run−2Source-diversity cap; one outlet shouldn't consume the budget.

Ties break on published_at descending, preserving today's behaviour exactly when everything else is equal. Weights live in one module-level table with a comment explaining they are a starting point to be tuned against Phase 0's data, not tuned constants pretending to be principled.

8.2 Free near-duplicate collapse before embedding (F10)

Normalize titles (lowercase, strip punctuation and any trailing "— Outlet" suffix), compare token sets by Jaccard similarity, cluster at ≥0.85, keep the highest-scoring member and mark the rest skip_reason="duplicate" with duplicate_of_article_id set — before the embedding call at ingestion.py:848. Pure-Python, no tokenizer dependency, and it removes exactly the syndicated-repost cluster that Google returns most of. The existing embedding dedupe stays as the semantic layer behind it.

8.3 Company-scoped URL dedupe (F12)

Decision (2026-07-30) — articles.url becomes unique per company. The unique constraint moves from url to (target_company_id, url), and the pre-insert check at ingestion.py:406 becomes company-scoped, so a story naming two tracked companies produces a signal for both instead of silently only for whichever the loop reached first.

Consequences to handle in implementation:

  • Spend. This deliberately increases AI cost on exactly the stories most likely to matter to several targets. It is bounded by the existing per-company cap (max_articles_per_company_per_run), which applies independently per company, so the worst case is linear in the number of companies a single story names.
  • Theme path. The cross-path rule in theme-search §6 — never create a ThemeMatch for a URL already covered by some company's Article — is unaffected: it is a global existence check, not a uniqueness constraint, and stays global.
  • Migration. Dropping a unique index and adding a composite one is straightforward; existing rows already satisfy the weaker constraint, so no data cleanup is needed. The downgrade path is not truly reversible once duplicate-URL rows exist — say so in the migration rather than pretending it round-trips.
  • Duplicate AI work across companies is still caught downstream: the same story ingested for two companies is embedded and summarized twice by design (each company gets its own outreach angle), but the per-company semantic dedupe is unaffected, since its candidate pool was already company-filtered (ingestion.py:858-873).
Assumption — no configuration knob for this. Per-company dedupe is simply the correct behaviour, so it ships unconditionally rather than behind a setting. If the extra spend turns out to matter, the lever is the existing per-company cap, not a scope toggle.

9. Phase 4 — URL resolution & enrichment

Phase 4 Turn headline-only items into real articles backend + migration size: L

Approved in §1 behind an admin toggle, off by default. Two independent steps, shippable separately.

9.1 Resolve the redirect to a canonical publisher URL (F9)

New nullable articles.canonical_url. url keeps the Google link as provenance; canonical_url is what the dashboard and the digest email link to when present, and what cross-source URL dedupe compares on. Two resolution strategies, tried in order:

  1. Decode the payload. The CBMi… segment is a base64 protobuf; current community decoders extract parameters from the article page and call Google's internal batchexecute endpoint. Fast and cheap when it works, but it is an unofficial internal API that has already changed once and will change again.
  2. Follow the redirect. A bounded GET with follow_redirects=True and a short timeout, reading the final URL. Slower, one request per article, but robust to Google changing its encoding.
Decision — implement the redirect-follow path first, keep decoding as an optimization behind the same interface. Resolution failure must be non-fatal: canonical_url stays NULL, everything falls back to today's behaviour. This also closes the open question in news-source-expansion §15 about redirect-link durability in digest emails a rep opens days later.

9.2 Pull a real snippet (F11)

With canonical_url known, fetch the publisher page through the SSRF-safe fetcher (§13) and extract, in order of preference: JSON-LD description, og:description, <meta name="description">. Store it in articles.description and set a new content_enriched boolean. Article.is_headline_only becomes:

return self.source == ArticleSource.GOOGLE_NEWS_RSS and not self.content_enriched

Everything downstream then improves for free: triage judges real text instead of a headline, supporting_quote becomes possible, the embedding stops being title-only (which also strengthens Phase 3's semantic dedupe), and the UI's lower-confidence labelling for this source stops applying to enriched items.

Budgets: per-run cap on enrichment fetches, per-domain serialization, total wall-clock ceiling, and enrichment attempted only for articles that survived scoring and the cap — never for the whole raw result set. Failure is silent and non-fatal: the article stays headline-only.

10. Phase 5 — Precision feedback loop

Phase 5 Let the app tell you which sources are wasting your budget backend + frontend size: M

Once Phase 0's data exists, per-domain precision is a straightforward aggregate: for each source_name/domain over the last 30 days, count signals created, signals dismissed, and articles triaged out. A domain with 40 fetched, 2 kept and 15 explicitly dismissed is a denylist candidate, and the Settings panel can say so with a one-click "add to denylist" that writes straight into the Phase 2 field.

This extends the same rule-based, no-LLM-call philosophy services/feedback.py already uses to derive ai_feedback_note from dismissal patterns — adding a domain dimension alongside the existing category dimension.

13. Security considerations

Phase 4 is the only part of this plan that changes the app's security posture: it makes the backend fetch URLs derived from third-party feed content. That is a textbook SSRF surface and must be built as such.

  • Scheme allowlist — https:// only (stricter than the existing is_safe_article_url, which permits http for display purposes).
  • DNS resolution guard — resolve first, reject loopback, link-local, private, CGNAT and reserved ranges; re-check after every redirect hop, not just the first (DNS rebinding).
  • Bounded everything — connect/read timeouts, max redirect hops, max response bytes, per-run fetch count, total wall-clock budget. An enrichment pass must never be able to extend an ingestion run indefinitely.
  • No credentials, ever — no cookies, no auth headers, no proxy credentials on these requests.
  • Parse defensively — extracted metadata is untrusted text: length-capped, HTML-stripped, and it flows into AI prompts, so it inherits the prompt-injection exposure the pipeline already has for titles/descriptions. Worth stating in the AI prompt that article-derived text is data, not instructions.
  • Off by default, admin-gated, with the toggle's help text naming the trade-off explicitly.

Phases 0–3 add no new outbound surface. The preview endpoint (§5.2) must be admin-only and rate-limited, since it triggers a real outbound request on demand — the same reasoning that already governs create_signal_from_skipped_article and /ingestion/run-now.

14. Test plan & acceptance criteria

  • build_google_news_query: identity-only; identity + aliases; context terms; exclusions; allowlist; denylist; when:; intitle:; and every combination at the word-budget boundary, asserting the documented drop order.
  • google_when_operator: bucket boundaries at 1h/12h/24h/7d and the >7d clamp.
  • Client: 200-with-entries; 429 → NewsClientError (not an empty list); 500 → retry then error; malformed XML → error; timeout is actually applied (assert the value reaches the httpx call).
  • article_mentions_company: an article containing only a context term must now be rejected — the direct regression test for F2.
  • Scoring: a newer aggregator repost loses to an older allowlisted original naming the company in its title.
  • Near-dup collapse: five syndicated variants of one headline yield one surviving article and four duplicate rows, with no embedding call made for the four.
  • Funnel counters: a fixture run produces drop_counts that sums correctly to articles_raw.
  • Migration: context_terms is populated from keywords, aliases is empty, and the generated query for an unedited company is byte-identical to the pre-migration query.
  • keywords stays synchronized with aliases + context_terms across create and update.
  • SSRF guard: private/loopback/link-local targets rejected, including on a redirect hop.
  • Preview endpoint: admin-gated, rate-limited, writes no articles rows and makes no AI call.
  • Company-scoped dedupe: one article naming two tracked companies produces a Signal for both; the theme path's global URL check still suppresses a ThemeMatch for that URL.
  • Allowlist resolution: NULL inherits the workspace list, [] emits no site: clause at all, a non-empty list replaces the workspace list entirely — and the denylist unions in every case.
  • Allowlist migration: an entity with an existing non-empty list produces a byte-identical query before and after the migration (union backfill), and an entity with an empty list becomes NULL and keeps inheriting.
  • Existing NewsAPI.org / NewsData.io / theme tests unchanged and passing — the §1 blast-radius decision is only real if this holds.

Acceptance for the whole effort is measured, not asserted: with Phase 0 shipped first, record a baseline week of drop_counts, triaged_out and dismissal rates for Google News, then compare after each phase. "Fewer noisy signals" has to show up as a lower triaged-out + dismissed fraction at equal or higher signal volume.
