Planning document — what the two statuses mean today, why they clutter the Signals table, and a concrete plan to fix it for low-technical end users

1. What's the difference, today

A Signal moves through four statuses (backend/app/models/signal.py:14-18): new → reviewed → one of archived / dismissed. Both of the terminal statuses are reached from the exact same two buttons everywhere a signal is shown (SignalRow.tsx, SignalDetail.tsx), and nothing in the UI currently explains the difference — no tooltip, no helper text, just the two German verbs. That ambiguity is itself a usability problem for a low-technical audience, before even getting to the clutter complaint.

Based on how the rest of the app already treats each status, the intended meaning is:

Archivieren (archived)Verwerfen (dismissed)
Meaning "This was a real, relevant signal — I'm done acting on it, but I want to keep it for the record." A positive/neutral conclusion. "This isn't relevant / it's noise / a false positive." A rejection — conceptually the same bucket as an article the AI triaged out before it ever became a signal.
Evidence in the codebase No dedicated view exists yet — it's purely a status label today (the gap this plan closes). SkippedFeed.tsx's "Übersprungen" page already bundles dismissed signals together with admin-only triaged-out articles under one page and one subtitle: "Alles, was die Pipeline nicht zu einem aktiven Signal gemacht hat" (signals.json:78) — i.e. the product already treats "dismissed" as equivalent to "never became a real signal," not as "a real signal I've filed away."
Restorable? Yes, via the status filter dropdown, but with no dedicated "put it back" affordance. Yes — SkippedFeed.transitionSignal already has a one-click restore + toast.
Good analogy for non-technical users An email "Archive" folder — done with it, not deleting it. An email "Trash"/spam action — actively saying this doesn't belong in my inbox.

2. Why they clutter the table anyway

The reported problem — dismissing/archiving many articles clutters the Signals table — is confirmed in code, and it's not because the concepts are wrong; it's because neither the filter default nor (for archived) any dedicated view actually removes them from view:

G1 — the default status filter is not actually "active only." SignalsFeed.tsx:40-42 defaults statusFilter to "", which means loadSignals() (SignalsFeed.tsx:52-53) sends no status query param at all. backend/app/api/signals.py:43-44 only filters by status when one is explicitly given, so with no filter every status — new, reviewed, archived, dismissed — comes back and is rendered in the same list, distinguished only by a small colored status-badge. The dropdown option is even labeled t("status.all") = "Alle Status," which is literally true but not what a user wants as their default working view.
G2 — dismissed got a second home, not a replacement home. v1-release-roadmap.html §2.4 added the "Übersprungen" (SkippedFeed.tsx) page specifically so dismissed signals had somewhere findable to live. But that page is additive — dismissed signals still also show up in the main table under "Alle Status" (see G1), so the roadmap item gave users a second place to find dismissed signals without removing them from the first place they were cluttering.
G3 — archived has no second home at all. Unlike dismissed, there is no archived_signal_count anywhere (backend/app/api/dashboard.py:49-62 computes new_signal_count and dismissed_signal_count but nothing for archived) and no archive-equivalent of SkippedFeed.tsx. The only way to stop seeing an archived signal is to manually pick a different value in the status filter dropdown — a discovery step most low-technical users won't take. Every signal a user archives just sits in the default table forever.
One thing already works: the Dashboard gets it right. dashboard.py:42 restricts its "top signals" panel to status IN (new, reviewed) specifically so archived/dismissed don't clutter that view. That's the exact behavior the main Signals table's default should also have — this plan brings the list page in line with a pattern the dashboard already proves out.

3. Goals & non-goals

Goals

  • Make the default Signals view show only actionable signals (new + reviewed) — archiving or dismissing a signal should visibly remove it from the list the user is working in, immediately, with no extra filter click required.
  • Give archived the same findability dismissed already has: a count and a dedicated place to browse/restore it, so archiving never feels like "did that just delete it?"
  • Make the difference between the two actions legible in the UI itself (tooltip/microcopy), not just inferable from behavior, since low-technical users won't read planning docs.
  • Preserve the existing undo-toast safety net (transitionSignal/ transitionSelected in SignalsFeed.tsx) exactly as is — it's the right pattern and already works well.

Non-goals (this pass)

  • Renaming the statuses themselves (archived/dismissed as data) or their German labels "Archivieren"/"Verwerfen" — see the open question in §9. This plan fixes visibility and clarity, not vocabulary, unless a naming change is separately confirmed.
  • Merging archived signals into the existing "Übersprungen" page — dismissed and archived have opposite emotional meaning (junk vs. a job well done) and merging them would recreate the exact ambiguity §1 is trying to resolve. They should have parallel but separate homes.
  • Changing how reviewed works — it stays an active, in-list status.

4. Key decisions

Default Signals view = active statuses, not literally all four. When no explicit status filter is chosen, both GET /signals and the dropdown's default should mean new + reviewed. A literal "every status including archived/dismissed" option stays available for anyone who wants full history, but it stops being the default and gets its own explicit label so it's never ambiguous which one is selected.
Archived gets a mirror of the Skipped page, not a merge into it. Add a dedicated Archive view (new page or a second section alongside "Übersprungen," reusing SignalRow and the same restore-with-toast pattern SkippedFeed.transitionSignal already implements). Keeps the "done, and I chose to keep it" meaning distinct from "junk, discard it."
Surface counts on the dashboard, following the existing pattern exactly. Add archived_signal_count to DashboardSummary (backend/app/schemas/dashboard.py) computed the same way dismissed_signal_count already is (dashboard.py:54), linking to the new Archive view — mirrors the comment already in the code: "so 'where did my skipped stuff go' has one visible answer instead of being buried in a filter dropdown."

5. Backend changes

FileChange
backend/app/api/signals.py list_signals: when status_filter is None and no explicit "all" sentinel is passed, filter to Signal.status.in_([SignalStatus.NEW, SignalStatus.REVIEWED]) instead of leaving the query unfiltered. Add support for an explicit status=all query value (not a real enum member) that skips the status filter entirely, for the one dropdown option that intentionally wants every status.
backend/app/api/dashboard.py Add archived_signal_count = followed_query.filter(Signal.status == SignalStatus.ARCHIVED).count() next to the existing dismissed_signal_count line (dashboard.py:54).
backend/app/schemas/dashboard.py DashboardSummary gains archived_signal_count: int.
backend/tests/test_signals_api.py, backend/tests/test_dashboard_api.py Add coverage: default GET /signals excludes archived/dismissed; explicit status=archived/status=dismissed/status=all still work; dashboard response includes the new count.

7. Copy & i18n (for low-technical users)

The single highest-leverage, lowest-risk change here is adding one line of explanatory copy to the two buttons — it needs no data model or filtering change to ship and directly addresses "our users don't know what these mean." Proposed additions to frontend/src/i18n/locales/de/signals.json / en/signals.json: 

"transitions": {
  "reviewed": "Als geprüft markieren",
  "archived": "Archivieren",
  "dismissed": "Verwerfen"
},
"transitionHints": {
  "archived": "Erledigt, aber aufbewahren — wird aus der aktiven Liste entfernt und im Archiv gespeichert.",
  "dismissed": "Nicht relevant — wird ausgeblendet, taucht aber weiterhin unter „Übersprungen“ auf."
}

These render as native title tooltips on the two buttons to start (zero layout risk); if usability feedback later shows tooltips aren't enough for this audience, promote the hint text to a visible one-line caption under each button as a follow-up, rather than bundling that layout change into this fix.

8. Implementation roadmap

Phase 1 Fix the clutter (backend + filter default)

§5's backend change plus the SignalsFeed.tsx dropdown default fix from §6. This alone solves the reported complaint: archiving or dismissing a signal makes it disappear from the default table immediately. Independently shippable, low risk, no new UI surface.

Phase 2 Explain the actions

The tooltip copy from §7. Ships alongside or right after Phase 1 — same files, no dependency either way.

Phase 3 Give archived a home

ArchivedFeed.tsx, the archived_signal_count dashboard card, and its nav entry. Depends on Phase 1's backend filtering support (status=archived already works today via the existing filter, so this phase is mostly additive frontend work).

9. Open questions

Where does the Archive view live in navigation? Two reasonable options: (a) a second section on the existing "Übersprungen" page, renamed to something like "Archiv & Übersprungen," or (b) its own nav entry / dashboard-linked page, parallel to but separate from Skipped. Given §3's non-goal of not conflating the two concepts, (b) is the safer default recommendation, but this needs a call before Phase 3 starts.
Should "Archivieren"/"Verwerfen" be renamed? The German verbs are correct and reasonably common, but not self-explanatory to a first-time low-technical user without the tooltip. This plan recommends shipping Phase 2's tooltip first and only considering a label change (e.g. to "Erledigt" vs. "Nicht relevant") if user feedback after that still shows confusion — changing labels people have already learned has its own cost, so it shouldn't be bundled into this fix without evidence it's needed.
Bulk action bar wording. SignalsFeed.tsx:340-348's bulk-selection action buttons reuse the same t(\`transitions.${status}\`) strings as the per-row buttons; the same tooltip treatment from §7 should extend there for consistency, but bulk buttons in a toolbar have less room for a hover tooltip to be discoverable — worth a quick UX check once Phase 2 is in front of real users.
