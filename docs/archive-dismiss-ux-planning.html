Archivieren vs. Verwerfen

Planning document — what the two statuses mean today, why they clutter the Signals table, and a concrete plan to fix it for low-technical end users

Status: Implemented (2026-08-13) on claude/archivieren-verwerfen-ux-elrhbi, with one change from the original proposal below confirmed by the stakeholder: rather than keeping "Verwerfen" as a lower-profile action, the dismiss transition was removed from the UI entirely — going forward "Archivieren" is the only way to move a signal out of the active feed. Existing dismissed signals are not migrated or deleted; they remain visible (and restorable) on the renamed Archive page, filterable separately from newly-archived ones. §4 and §9 are updated accordingly; §1–§3's analysis of why the two statuses existed and why they cluttered the table still stands as the record of the problem this fix addresses.
Builds on: v1-release-roadmap.html §2.4 (shipped the "Übersprungen"/Skipped page this page replaces), dashboard-favorites-todos-planning.html (the dashboard counts pattern this plan reuses)
Doc purpose: Explain the intended semantics of archived vs. dismissed signal status, confirm in code why both still clutter the default Signals view despite §2.4's fix, and record the plan this session implemented directly from it.

1. What's the difference, today

A Signal moves through four statuses (backend/app/models/signal.py:14-18): new → reviewed → one of archived / dismissed. Both of the terminal statuses are reached from the exact same two buttons everywhere a signal is shown (SignalRow.tsx, SignalDetail.tsx), and nothing in the UI currently explains the difference — no tooltip, no helper text, just the two German verbs. That ambiguity is itself a usability problem for a low-technical audience, before even getting to the clutter complaint.

Based on how the rest of the app already treats each status, the intended meaning is:

Archivieren (archived)Verwerfen (dismissed)
Meaning "This was a real, relevant signal — I'm done acting on it, but I want to keep it for the record." A positive/neutral conclusion. "This isn't relevant / it's noise / a false positive." A rejection — conceptually the same bucket as an article the AI triaged out before it ever became a signal.
Evidence in the codebase No dedicated view exists yet — it's purely a status label today (the gap this plan closes). SkippedFeed.tsx's "Übersprungen" page already bundles dismissed signals together with admin-only triaged-out articles under one page and one subtitle: "Alles, was die Pipeline nicht zu einem aktiven Signal gemacht hat" (signals.json:78) — i.e. the product already treats "dismissed" as equivalent to "never became a real signal," not as "a real signal I've filed away."
Restorable? Yes, via the status filter dropdown, but with no dedicated "put it back" affordance. Yes — SkippedFeed.transitionSignal already has a one-click restore + toast.
Good analogy for non-technical users An email "Archive" folder — done with it, not deleting it. An email "Trash"/spam action — actively saying this doesn't belong in my inbox.

2. Why they clutter the table anyway

The reported problem — dismissing/archiving many articles clutters the Signals table — is confirmed in code, and it's not because the concepts are wrong; it's because neither the filter default nor (for archived) any dedicated view actually removes them from view:

G1 — the default status filter is not actually "active only." SignalsFeed.tsx:40-42 defaults statusFilter to "", which means loadSignals() (SignalsFeed.tsx:52-53) sends no status query param at all. backend/app/api/signals.py:43-44 only filters by status when one is explicitly given, so with no filter every status — new, reviewed, archived, dismissed — comes back and is rendered in the same list, distinguished only by a small colored status-badge. The dropdown option is even labeled t("status.all") = "Alle Status," which is literally true but not what a user wants as their default working view.
G2 — dismissed got a second home, not a replacement home. v1-release-roadmap.html §2.4 added the "Übersprungen" (SkippedFeed.tsx) page specifically so dismissed signals had somewhere findable to live. But that page is additive — dismissed signals still also show up in the main table under "Alle Status" (see G1), so the roadmap item gave users a second place to find dismissed signals without removing them from the first place they were cluttering.
G3 — archived has no second home at all. Unlike dismissed, there is no archived_signal_count anywhere (backend/app/api/dashboard.py:49-62 computes new_signal_count and dismissed_signal_count but nothing for archived) and no archive-equivalent of SkippedFeed.tsx. The only way to stop seeing an archived signal is to manually pick a different value in the status filter dropdown — a discovery step most low-technical users won't take. Every signal a user archives just sits in the default table forever.
One thing already works: the Dashboard gets it right. dashboard.py:42 restricts its "top signals" panel to status IN (new, reviewed) specifically so archived/dismissed don't clutter that view. That's the exact behavior the main Signals table's default should also have — this plan brings the list page in line with a pattern the dashboard already proves out.

3. Goals & non-goals

Goals

  • Make the default Signals view show only actionable signals (new + reviewed) — archiving or dismissing a signal should visibly remove it from the list the user is working in, immediately, with no extra filter click required.
  • Give archived the same findability dismissed already has: a count and a dedicated place to browse/restore it, so archiving never feels like "did that just delete it?"
  • Make the difference between the two actions legible in the UI itself (tooltip/microcopy), not just inferable from behavior, since low-technical users won't read planning docs.
  • Preserve the existing undo-toast safety net (transitionSignal/ transitionSelected in SignalsFeed.tsx) exactly as is — it's the right pattern and already works well.

Non-goals (this pass)

  • Renaming the archived/dismissed statuses as data, or the "Archivieren" label — see §9's resolved question. Update: "Verwerfen" ended up removed as an action rather than renamed or merely re-homed; see §4's confirmed decisions.
  • Changing how reviewed works — it stays an active, in-list status.

Update — one originally-listed non-goal was overridden by the stakeholder: this document originally argued against merging archived signals into the "Übersprungen" page, reasoning that archived and dismissed have opposite emotional meaning and merging would recreate §1's ambiguity. The confirmed decision (§4, §9) merged them anyway, into a single filterable Archive page — a filter row picking "Archiviert" vs. "Verworfen" turned out to be enough to keep the two legible side by side without needing separate pages, and consolidating both plus the admin skipped-articles queue behind one nav entry was judged more valuable for a low-technical audience than three destinations.

4. Key decisions

Default Signals view = active statuses, not literally all four. When no explicit status filter is chosen, both GET /signals and the dropdown's default should mean new + reviewed. A literal "every status including archived/dismissed" option stays available for anyone who wants full history, but it stops being the default and gets its own explicit label so it's never ambiguous which one is selected.
Surface counts on the dashboard, following the existing pattern exactly. Add archived_signal_count to DashboardSummary (backend/app/schemas/dashboard.py) computed the same way dismissed_signal_count already is (dashboard.py:54), linking to the new Archive view — mirrors the comment already in the code: "so 'where did my skipped stuff go' has one visible answer instead of being buried in a filter dropdown."
Confirmed with stakeholder (2026-08-13) — three changes to the plan above:
  1. "Verwerfen" is removed as an action, not just re-homed. STATUS_TRANSITION_VALUES (constants/signalStatus.ts) drops "dismissed" entirely, so the button disappears from SignalRow, SignalDetail, and the bulk-action toolbar everywhere at once — "Archivieren" is the only way forward to move a signal out of the active feed. The dismissed status itself is not removed from the data model or API: existing dismissed signals keep their status and stay visible/restorable on the Archive page, they just can't be created anymore.
  2. One merged Archive page, not a mirror of the Skipped page. Rather than giving archived signals their own separate view alongside "Übersprungen," the renamed /archive page (ArchiveFeed.tsx, replacing SkippedFeed.tsx) shows archived and dismissed signals together in one list, with a filter (Alle / Archiviert / Verworfen) to narrow the view — plus the existing admin-only triaged-out-articles section, unchanged. This supersedes the "mirror, not merge" recommendation this document originally made.
  3. Tooltip hint extends to the bulk-action toolbar too (§7's suggestion, confirmed rather than deferred): the same transitionHints.archived string renders as the title on both the per-row button and the toolbar's bulk "Archivieren" button.

6. Frontend changes (as shipped)

FileChange
frontend/src/constants/signalStatus.ts STATUS_TRANSITION_VALUES changed from ["reviewed", "archived", "dismissed"] to ["reviewed", "archived"]. Because every transition button in the app (row actions, detail-page actions, bulk-toolbar actions, and the Themes page's topic-match actions, which share this same constant) is generated from this list, removing "dismissed" here removed the "Verwerfen" button everywhere in one change.
frontend/src/pages/SignalsFeed.tsx SIGNAL_STATUSES (the status-filter dropdown's options) shrank to ["new", "reviewed"] — archived and dismissed are no longer offered as filters here at all, since they now live on the Archive page. The empty-value "Alle Status" default option was kept as-is; it now means "active statuses" because the backend defaults that way. Also removed the dead status === "dismissed" branches from transitionSignal/ transitionSelected (unreachable now that "dismissed" is never a transition target from this page) and added the §7 tooltip to the bulk-action toolbar's "Archivieren" button.
frontend/src/pages/ArchiveFeed.tsx (renamed from SkippedFeed.tsx) Fetches both GET /signals?status=archived and GET /signals?status=dismissed, merges them into one list sorted by recency, and renders it through SignalRow with a filter select (Alle / Archiviert / Verworfen) that narrows the displayed subset client-side. Restoring a signal (via the same SignalRow transition buttons — now just "Geprüft" / "Archivieren", per the constant change above) removes it from the list, same pattern SkippedFeed.transitionSignal used. The admin-only triaged-out-articles section is carried over unchanged beneath it.
frontend/src/App.tsx Route moved from /skipped to /archive; the /settings/review redirect now points at /archive. No redirect shim for the old /skipped path, consistent with this app's existing internal-tool-only convention (see dashboard-favorites-todos-planning.html §9).
frontend/src/pages/Dashboard.tsx Replaced the conditional "N skipped" stat with an always-visible "Archiv" button/stat linking to /archive, showing archived_signal_count + dismissed_signal_count + skipped_article_count combined — this is the "button on the homepage" the user asked for.
frontend/src/components/SignalRow.tsx, frontend/src/pages/SignalDetail.tsx Added a title attribute (native tooltip) to each transition button, reading transitionHints.<status> with an empty-string fallback so "Geprüft" (which has no hint) silently gets no tooltip. Also dropped the now-dead dismissedToast branch from SignalDetail.updateStatus.

7. Copy & i18n (for low-technical users)

The single highest-leverage, lowest-risk change here was adding one line of explanatory copy to the archive button — no data model or filtering change needed, and it directly addresses "our users don't know what this does." Shipped additions to frontend/src/i18n/locales/de/signals.json / en/signals.json (the dismissed transition/hint entries were dropped along with the button itself): 

"transitions": {
  "reviewed": "Als geprüft markieren",
  "archived": "Archivieren"
},
"transitionHints": {
  "archived": "Erledigt, aber aufbewahren — wird aus der aktiven Liste entfernt und im Archiv gespeichert."
}

These render as native title tooltips on the button, on both the per-row/detail-page instance and the bulk-action toolbar instance (§4's third confirmed change). If usability feedback later shows a hover tooltip isn't enough for this audience, promoting the hint text to a visible one-line caption under the button is the natural next step — not bundled into this pass.

8. Implementation roadmap (as shipped)

Done Remove "Verwerfen," fix the clutter

STATUS_TRANSITION_VALUES dropped "dismissed"; GET /signals defaults to active statuses only; SignalsFeed.tsx's filter dropdown shrank to new/reviewed. Together these mean archiving a signal (the only remaining transition off the active list) makes it disappear from the default table immediately, and there is no longer a UI path to create new dismissed signals.

Done Explain the action

The §7 tooltip, on both the per-row/detail button and the bulk-toolbar button.

Done Give archived (and legacy dismissed) a home

ArchiveFeed.tsx at /archive (renamed from SkippedFeed.tsx / /skipped), combining archived + dismissed signals with a filter, plus the always-visible "Archiv" button on the Dashboard homepage and the archived_signal_count it depends on.

9. Resolved questions

The three open questions this document originally raised were resolved directly by the stakeholder before implementation (2026-08-13):

Where does the Archive view live? — merged, not mirrored. Contrary to this document's original (b)-leaning recommendation, the confirmed answer combined archived and dismissed signals into one renamed page (/archive, replacing "Übersprungen") with a filter to switch between "Alle" / "Archiviert" / "Verworfen," rather than giving archived its own separate page. See §4's third confirmed decision.
Should "Archivieren"/"Verwerfen" be renamed? — narrower than either option this document posed. Neither "keep both labels" nor "rename both" — "Verwerfen" is removed as an action entirely, and "Archivieren" keeps its existing label unchanged. The historical dismissed status itself keeps its "Verworfen" label wherever it's still displayed (the status badge, the Archive page's filter), since that's describing data, not offering an action.
Bulk action bar wording — confirmed as suggested. The tooltip treatment from §7 extends to the bulk toolbar's "Archivieren" button, per the recommendation this document made.
NewsAtlas — planning document. Written to answer "what's the difference between Archivieren and Verwerfen," to close the gap between what the two statuses were supposed to mean and what the Signals table actually showed, and — after stakeholder confirmation — implemented directly from §4–§7 above.
