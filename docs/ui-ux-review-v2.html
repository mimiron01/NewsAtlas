NewsAtlas — UI/UX Review v2

A second pass through the frontend, this time reading it through Don Norman's The Design of Everyday Things and the "Laws of UX" (lawsofux.com) rather than Nielsen's heuristics — looking for gaps a different lens surfaces once the obvious ones are already fixed.

Scope: React/TypeScript SPA in frontend/ — every page, every shared component, styles.css, and the i18n resource files (en/de)
Reviewed at: commit 3984a7c
Method: manual source read of every page/component, cross-checked against the app's own routes, translation strings, and CSS — no dynamic/browser testing performed
Not in scope: backend API design, data model, deployment/security posture, and the email digest (see docs/security-review.html and F9 of v1)
Relation to docs/ui-ux-review.html (v1). The first review used Nielsen's 10 usability heuristics and found 13 issues (F1–F13), all of which were implemented in that same pass: responsive layout, confirm-before-delete, inline/bulk triage, onboarding checklist, toasts/skeletons, search/sort, icons/motion, focus states, dark mode, page titles. This review does not re-litigate those — reading the current code, all thirteen are genuinely in place. Since then the product has grown substantially (topic/theme tracking, a dashboard, todos, favorites, CSV import, admin roles, full German localization, per-source usage diagnostics), which is both new surface area and a chance to look at the whole thing again with a different analytical toolkit. Findings below are new; where v1 and this review land on the same screen, it's from a different angle.

NewsAtlas has clearly had real design attention already — the positives section below is longer than a typical first-pass review's, and several patterns here (the tri-state source-allowlist field, the duplicate-topic conflict resolution, the optimistic-UI-with-undo toast on dismiss) are genuinely well-executed applications of Norman's principles without anyone necessarily having named them that way. The gaps found this time are correspondingly narrower: not "there is no confirmation before delete" but "the confirmation is one fast double-click away from not working"; not "there is no dark mode" but "seven same-sized badges compete for attention on one signal." That's a sign of a maturing product, and the findings are prioritized accordingly.

Norman's six design principles, applied

The Design of Everyday Things organizes good design around six concepts: affordances (what actions an object makes possible), signifiers (the perceivable signals that communicate those affordances), constraints (limits that narrow the possible actions to the sensible ones), mapping (the relationship between a control and its effect), feedback (continuous information about the result of an action), and the conceptual model (the mental picture the design gives the user of how the system works). Scored against the current frontend:

PrincipleRatingNotes
AffordancesGoodButtons look clickable, links look like links, disabled controls are visually dimmed and inert — nothing pretends to be interactive when it isn't, or vice versa.
SignifiersPartialIcon+label nav items and the favorite star (filled vs. outline, aria-pressed) signify state well. Persistent toggles like mute/pause/digest-include don't (F3).
ConstraintsGoodSourceAllowlistField's inherit/all/custom radio group is a genuinely good example: it exposes the real three-state model as three mutually exclusive, always-visible options rather than one ambiguous checkbox + text field.
MappingPartialMost controls map cleanly (a checkbox toggles a boolean setting, a select picks from a real enum). Country/language edition fields don't (F4).
FeedbackGoodOptimistic updates, toasts (including an actual Undo action on dismiss), and a granular ingestion-progress bar with per-company/per-article text are all strong, continuous feedback loops — this is the area v1's F5/F10 clearly paid off in.
Conceptual modelPartialThe 409 duplicate-topic conflict is a model example of surfacing the system's real state and offering a way forward (F below, positives). Login's model of "how do I get back in if I forget my password" is simply absent (F8).

F1. Hick's Law — action overload in dense list rows Medium

Hick's Law: the time it takes to decide grows (logarithmically) with the number of choices on offer. Six visually identical buttons force the same scan-and-decide cost onto every row, every time.

frontend/src/pages/ThemesPage.tsx:910-965 (Run · Edit · Mute/Unmute · Include/Exclude from digest · Pause/Resume · Delete — up to 6 buttons per topic) and frontend/src/pages/SettingsTargets.tsx:441-505 (Backfill · Edit · Mute/Unmute · Pause/Resume · Delete — up to 5 per company)

Issue

Both list screens render every possible action for every row, all the time, all styled identically (plain or secondary text buttons of equal size and weight). A workspace at the default active-topic cap of 10 puts up to 60 individually-styled buttons on screen simultaneously on the Topics page alone. None of the six is visually more important than another — "Delete" and "Mute" carry the same visual weight as "Edit" — so a user re-derives which button they want from scratch on every row instead of recognizing a stable, small set of primary actions. This is the same problem F1 (of this review) and F3 (of v1) were solving on the signals feed a layer up — but it's been re-introduced here as new features (topics, per-row digest toggle, backfill) were added, each contributing one more always-visible button.

Suggested direction

Reduce the number of simultaneously visible controls by promoting the 1–2 actions a user reaches for most (Run, Edit) and moving the rest behind a single "⋯" overflow menu — a pattern the app doesn't use yet anywhere, but one both Nielsen's recognition over recall and Hick's Law point toward for a row with this many possible actions.

  1. Keep ThemeRunButton and "Edit" inline (the two most frequent actions); move Mute, digest include/exclude, Pause/Resume, and Delete into a small popover menu triggered by a "⋯" icon button, reusing the same open/close-on-outside-click pattern already implemented in ProfileMenu.tsx and HelpTooltip.tsx rather than inventing a new one.
  2. Keep Delete's confirm step inside the menu rather than the row, which also resolves part of F2 below by moving the second click away from the first click's screen position.
  3. Apply the same treatment to the target-companies table's action column.

F2. A confirm-before-delete that a fast double-click defeats High

Fitts's Law: a target that is closer and appears faster is reached faster — including by an unintended second click. A confirm step only works as a safety net if the second click has to be a deliberate, separate action, not the accidental continuation of the first.

frontend/src/pages/SettingsTargets.tsx:481-504 and frontend/src/pages/ThemesPage.tsx:940-963 — confirmingId state swaps the button label in place

Issue

Clicking "Delete" (or "Unfollow") re-renders that exact button, in the exact same row position, as "Confirm delete." A double-click — a completely ordinary motor pattern, and the default way many users dismiss anything unfamiliar that just appeared — lands its second click on "Confirm delete" before the label has even been read, because nothing about the position, timing, or size of the target changed between the two clicks. The confirmation step (added specifically to prevent accidental data loss, per v1 F2) is real in the code but not reliably real in practice for exactly the fast, careless interaction it exists to guard against. This is worse in the two screens this review is looking at (Topics, Target Companies) than it was when v1 first added the pattern, because both now sit inside a row of 5-6 buttons (F1), so a slightly-mis-aimed click elsewhere in that row is also more likely to land on Delete in the first place.

Suggested direction

Break the spatial and temporal identity between the two clicks, using whichever of these fits the row-simplification in F1:

  1. If F1's overflow menu ships: the problem mostly resolves itself — closing and reopening a menu, then clicking a differently-positioned confirm item inside it, isn't the same reflexive gesture as a double-click on one spot.
  2. Independent of F1: disable the "Confirm delete" button for ~400-500ms after it appears (long enough to break a double-click, short enough not to feel laggy — see the Doherty Threshold), or render it in a visually distinct location (e.g. sliding the row into a confirmation state with the button in a new position) rather than as a same-slot label swap.
  3. Either way, this is the kind of change worth a quick manual double-click test on the built app before calling it done — the current implementation "looks" fixed reading the JSX in isolation, which is exactly why it's easy to miss without exercising the actual click sequence.

F3. Missing signifiers for persistent on/off state Medium

Signifiers are what make an affordance perceivable — the visual signal that tells you not just that something can be clicked, but what state it's in and what clicking it will do. A button that reads "Mute" and a button that reads "Unmute" are two different signifiers for two different moments, but both look identical to every other button in the row.

frontend/src/pages/ThemesPage.tsx:924-934 (mute/unmute, digest include/exclude), frontend/src/pages/SettingsTargets.tsx:465-471 (mute/unmute), frontend/src/pages/ThemesPage.tsx:935-939 and SettingsTargets.tsx:472-480 (pause/resume)

Issue

Mute/pause/digest-inclusion are all durable, binary states of a topic or company — closer to a light switch than a doorbell. But they're rendered exactly like one-shot actions ("Edit", "Delete"): a text button whose label happens to change based on state. The digest button goes slightly further by adding className="secondary" when include_in_digest is true (ThemesPage.tsx:929), but that's a subtle style difference easy to miss at a glance, and it isn't applied to the mute or pause/resume buttons at all — so those two convey their current state purely through which word is currently printed on them. A user scanning a list of 10 topics to find which ones are currently muted has to read every button's label individually; a real toggle would let that same scan happen at a glance, which is the entire reason switches look different from buttons in every mainstream design system.

Suggested direction

  1. Introduce a small reusable toggle-switch component (no library needed — a styled <button role="switch" aria-checked> with an on/off thumb, following the same hand-rolled-component convention already used throughout this codebase) and use it for mute, pause, and digest-inclusion in place of the current label-swapping buttons.
  2. Keep "Edit" and "Delete" as buttons — they're genuinely actions, not states, so they shouldn't change shape; the point is to make the two categories look different from each other, not to convert everything to switches.

F4. Weak mapping: free text for a closed set of values Low

Mapping is the relationship between a control and its effect. A free-text field maps to "any string the user types," but the actual valid domain here (Google News edition/language codes) is small and fixed — the control offers far more freedom than the data model can use, and a typo fails silently rather than being structurally impossible.

frontend/src/pages/ThemesPage.tsx:691-709,850-869 and frontend/src/pages/settings/SourcesTab.tsx:216-236 — plain <input> for google_news_country/google_news_language

Issue

Country and language are entered as free text (uppercased/lowercased on change, but not validated against a real list), with the workspace default shown only as placeholder text. Google News RSS supports a known, finite set of edition codes; a plain text input can't distinguish a valid code from a typo ("DE" vs "ED") until a live query preview or an actual fetch quietly returns nothing. The app already has the query-preview infrastructure (useThemeQueryPreview, ThemeQueryPreviewPanel) to catch this after the fact, but preventing the mistake at the control level — the way SourceAllowlistField and ThemeSourceSelector already do for their own closed sets, via radio/checkbox groups instead of text — would be more in line with how the rest of the form is built.

Suggested direction

  1. Replace the free-text country/language inputs with a <select> (or a searchable combobox if the valid list is long) populated from the actual set of codes the backend's Google News integration accepts, with "Inherit workspace default (…)" as the first option in place of the current placeholder-only hint.
  2. If the valid set genuinely isn't enumerable server-side today, that's worth fixing at the API layer first — a UI-level allowlist would otherwise drift from what the backend actually accepts.

F5. Miller's Law: dense forms with no progressive disclosure Medium

Miller's Law: working memory holds about seven items, plus or minus two, at once. A form that shows everything it's capable of, all the time, asks the user to hold the whole thing in mind even when nine-tenths of it is "leave this at its default."

frontend/src/pages/ThemesPage.tsx:614-733 (add-topic form, ~11 distinct fields across 3 sections) and frontend/src/pages/settings/SourcesTab.tsx:215-357 (Google News RSS block, ~12 fields once enabled)

Issue

Credit where it's due: the add-topic form already groups its fields under three named .form-section headings ("Criteria", "Sources", "Region") rather than one undifferentiated stack — that's real progressive structure, just not progressive disclosure. Every field in every section is visible and interactive the moment the form opens, including the ones almost nobody needs to touch on a given topic (source denylist, edition/language overrides, source allowlist). Query terms and exclude terms are the two fields that matter for 90% of topics; the other ~7 are there for the remaining 10%, but they cost the same visual/cognitive attention either way. The Google News RSS settings block has the same shape at a larger scale: once the source is enabled, country, language, rate limit, allowlist, denylist, a time-operator checkbox, a query-strategy select, a resolve-URLs checkbox, and (conditionally) a fetch-snippets checkbox with two more numeric fields all render at once — a genuinely rare combination for one admin to tune in a single sitting.

Suggested direction

The app already uses <details>/<summary> for exactly this purpose elsewhere (CompanyTab.tsx's "show example" and SourcesTab.tsx's "recent activity" table) — extend that same pattern rather than introducing a new one:

  1. On the add-topic form, keep Name, Query terms, and Exclude terms visible by default; collapse Sources and Region behind a single "Advanced options" <details>, open automatically when editing a topic that already has non-default values set (so nothing an existing topic relies on becomes hidden by surprise).
  2. On the Google News RSS block, keep the enable checkbox, country/language, and allowlist/denylist visible (they're the fields most topics/companies actually touch); move the time-operator, query-strategy, resolve-URLs, and snippet-enrichment controls into their own collapsed "Advanced" section.

F6. Critical guidance trapped in hover-only tooltips Medium

Visibility of system status (and, concretely, the native title attribute never fires on touch — there is no hover state to trigger it). Explaining why a disabled control is disabled is only useful if the explanation is reachable on the device the user is actually holding.

frontend/src/components/ThemeRunButton.tsx:48 (why a per-topic "Run" is blocked), frontend/src/pages/SettingsTargets.tsx:499 and frontend/src/pages/ThemesPage.tsx:958 (delete/unfollow confirmation copy)

Issue

v1's F1 gave the app a genuine responsive layout with a mobile nav drawer, which is exactly the kind of investment that makes this finding worth flagging: the app now clearly intends to be used on a phone, but a few pieces of explanatory copy still only reach a mouse. ThemeRunButton disables itself for four different reasons (source disabled, topic paused, a run already in progress, still in cooldown) and explains which one via title={blockedReason} — invisible with no cursor to hover. The delete/unfollow row similarly explains its consequences (whether this company/topic has other followers, whether the current user is an admin) only via title on the initial "Delete" button, before the confirm step appears. A touch user sees a button that's disabled or destructive with no accessible explanation for either.

Suggested direction

  1. For ThemeRunButton, render blockedReason as visible field-hint text directly under the button when it's disabled, rather than (or in addition to) the title — it's short, and the button is already the kind of isolated control where a line of muted text underneath reads cleanly.
  2. For the delete/unfollow confirmation copy, this is already solved once the confirm step is showing (SettingsTargets.tsx:506 renders confirmCopy as a visible <p>, correctly) — the gap is only the pre-confirm hint on the initial button. Given F1's proposed overflow menu, the simplest fix is to always show the confirm-step copy immediately rather than gating it behind a first click at all, since the menu already adds one extra deliberate step before Delete is reachable.

F7. Von Restorff Effect: badge overload flattens hierarchy Medium

Von Restorff Effect (the Isolation Effect): in a set of similar items, the one that looks different is the one that gets noticed and remembered. Badges exist to make a piece of state jump out — that only works if not everything around it is also a badge.

frontend/src/pages/SignalDetail.tsx:162-186 (.signal-detail-badges: favorite, status, score, signal type, confidence, source, limited-detail — up to 7 elements) and frontend/src/components/SignalRow.tsx:33-45 (status, score, source, limited-detail, todo-pill — up to 5 per row)

Issue

Every one of these renders as the same shape: a small rounded pill, 0.68rem, bold, with a background/foreground pair from a fixed palette (styles.css:505-541). Status, relevance score, signal type, confidence, source, and "limited detail" are not equally important to a salesperson scanning the feed — status (is this new?) and relevance score (is this worth my time?) are the two things that actually drive the triage decision, but visually they carry exactly as much weight as "source: Google News" or "limited detail," which are closer to metadata. With up to 7 pills wrapping across two lines on a signal's detail page, nothing is the one thing your eye lands on first — which is the opposite of what a badge is normally for.

Suggested direction

  1. Establish two tiers: keep status and relevance score as solid, colored pills (the current .status-badge/.score-badge treatment they already have); demote signal type, confidence, source, and limited-detail to a plain inline text row (small, muted, no pill background) — still present and scannable, but visually secondary rather than competing for the same attention.
  2. This is a CSS-only change (new modifier classes, no new markup) so it's low-risk to try, and it can be done incrementally — start with SignalDetail.tsx, where the problem is most visible, then apply the same tier split to SignalRow.tsx once the split feels right there.

F8. No account-recovery path — a broken conceptual model High

Conceptual model: good design gives the user a correct mental picture of how to get what they need from the system. A login form with only "sign in" and "sign up" tells a locked-out user, implicitly and incorrectly, that those are their only two options.

frontend/src/pages/Login.tsx — entire component; no forgot-password link, route, or fallback copy anywhere in the auth flow

Issue

There is no "Forgot password?" link on the login form, no password-reset route in App.tsx, and no copy anywhere suggesting what to do if a password is lost (e.g. "ask a workspace admin to help you back in"). For a self-hosted B2B tool with invite-code signup and no visible admin contact info in the product itself, a locked-out user's actual options — ask whoever manages the deployment, or lose access entirely — are both invisible from inside the app. This is a real, not hypothetical, dead end: password managers fail, people change laptops, and a 10-character-minimum password (Login.tsx:74) is exactly memorable enough to be forgotten and exactly complex enough not to be guessed back.

Suggested direction

The right-sized fix depends on what the backend can support, but the UI-facing minimum is to stop the conceptual model gap, not necessarily to ship full self-service reset in this pass:

  1. Minimum: add a line of static copy under the password field or the sign-in button — "Forgot your password? Ask a workspace admin to help you back in" — so the app at least tells the truth about what's possible today, the same way it already does for the invite-code field.
  2. Fuller fix: if the backend can support it, a standard email-based reset flow (request → emailed token → new-password form) is the expected default for this category of product (Jakob's Law: users bring the mental model of every other login form they've used) — this would need backend work beyond this frontend-scoped review, so it's flagged here as the direction rather than specified in detail.

F9. Goal-Gradient Effect: hard caps surface only as failure Low

Goal-Gradient Effect: motivation and effort increase as a visible goal gets closer. A limit that's only ever seen at the moment it's hit can't do that — worse, it turns a plan-ahead moment into a surprise-and-redo moment.

frontend/src/pages/ThemesPage.tsx:305-310,381-386 (activeCeilingReached error, shown only after a failed create/activate call) vs. ThemesPage.tsx:736 (t("themes:trackedThemes", { count: themes.length }) — shows a raw count, not count-vs-limit)

Issue

Workspaces have a configurable ceiling on active topics (max_active_theme_watches, default visible/editable in CompanyTab.tsx:157-169). Nothing on the Topics page itself shows progress toward that ceiling — the heading just says "Tracked topics (7)" the same way whether the cap is 10 or 1000. The only way to learn the cap exists is to hit it: create or reactivate one topic too many and get an error toast after the fact. This is a small thing, but it's backwards from how limits usually help rather than frustrate — seeing "7 of 10 active" while you still have three to spare lets you plan (which topic matters least, if you're about to add a new one); finding out only via a failed submit does not.

Suggested direction

  1. Change the heading to show both numbers once max_active_theme_watches is known (already loaded workspace-wide via /settings/public as publicSettings, or via /settings for admins) — e.g. "Tracked topics (7 of 10 active)".
  2. Optionally style it as a small progress bar once within ~1-2 of the cap, reusing the existing .progress-bar/.progress-bar-fill classes already used for ingestion progress — the same visual language, applied to a different kind of "how close am I" question.

F10. Peak-End Rule: "you're caught up" reads as "you haven't started" Low

Peak-End Rule: people judge an experience mostly by its most intense moment and how it ends, not its average. Finishing your queue for the day is the natural "end" of the daily triage habit this product is built around — it's worth a different feeling than the empty state a brand-new, empty workspace shows.

frontend/src/pages/SignalsFeed.tsx:507-511 and frontend/src/i18n/locales/en/signals.json:110 — feed.noSignalsYet: "No signals yet. Add target companies and click "Fetch new signals" to get started."

Issue

This exact copy renders whenever the (filtered) signal list is empty — which includes both a genuinely new, empty workspace and an established workspace where a user has just filtered to status=new and triaged every last one. In the second case the message is not just flat, it's actively wrong: it tells someone who has already added companies and already fetched signals to go add companies and fetch signals. The daily-triage habit this product is designed around (see the README's own framing: "surfaces the result as actionable sales signals... to triage") means this "queue: zero" moment is one a returning user will hit often — arguably more often than the true first-run empty state v1's F4 was built to soften.

Suggested direction

  1. Distinguish the two cases already reachable from state on the page: if hasSomethingToFetch is true (companies or topics exist) and at least one ingestion run has ever completed, show a distinct "You're all caught up" message instead of the current one — same EmptyStateIllustration, different copy, maybe a subtly different (celebratory rather than instructional) tone.
  2. Reserve the current "add companies, click fetch" copy for the case that's actually true today: zero companies/topics and zero signals ever.

F11. Blank screen during startup, no visibility of system status Low

Visibility of system status (Nielsen, but also the baseline every other law in this review assumes): the one moment the app has literally nothing on screen is the very first paint, before the user has any evidence the app is working at all.

frontend/src/main.tsx:13 — <Suspense fallback={null}> around the i18next-suspended app tree

Issue

i18next is configured with react: { useSuspense: true }, and the top-level Suspense boundary's fallback is null — so between the initial HTML paint and the moment translation resources finish initializing, the page is a blank white (or, in dark mode, blank near-black) rectangle with no favicon-adjacent spinner, skeleton, or even the static "NewsAtlas" wordmark. Translation resources are bundled locally (not fetched over the network — see i18n/index.ts's static imports), so in practice this window is very short, which is exactly why it's rated Low rather than Medium; but it's also exactly the kind of gap that gets worse invisibly as the app grows (more locale files, more namespaces) without anyone noticing, since it never throws an error — it just sits blank a little longer each time.

Suggested direction

  1. Replace fallback={null} with a minimal static shell — even just the "NewsAtlas" wordmark or the existing Skeleton component — so first paint always shows something recognizable rather than an empty rectangle indistinguishable from a crashed or slow-loading page.

What's already working well

Feedback (Norman) + Peak-End Rule, done right The dismiss-with-undo toast (SignalsFeed.tsx:232-237, SignalDetail.tsx:56-61) is a genuinely good micro-interaction: it gives immediate feedback, treats a destructive-feeling action as reversible without a blocking confirm dialog, and gives that specific moment (letting go of a signal) a soft landing rather than an abrupt one. This is the pattern the Peak-End findings above (F10) are asking to see extended elsewhere, not introduced from scratch.
Conceptual model, done right The duplicate-topic 409 conflict (ThemesPage.tsx:296-315, mirrored in TopicTemplateGallery.tsx) is a textbook example of what Norman means by giving people a way to recover from an error rather than just reporting one: instead of a bare "a topic with this name already exists," it shows the existing topic's terms and offers exactly two clear paths forward (follow the existing one, or pick a different name) — no dead end, no guessing.
Constraints (Norman), done right SourceAllowlistField's inherit/all/custom radio group models a genuinely three-state field (not a boolean-plus-optional-text-field, which is what most apps would have shipped) as three mutually exclusive, always-visible, correctly-labeled options — the UI's structure matches the data model's structure exactly, which is the whole point of good mapping and good constraints working together.
Jakob's Law The checkbox-per-row + "select all" + contextual bulk-action bar pattern is now consistently reused across the Signals feed, the Target Companies table, and the Topics list — a shape borrowed from Gmail-style triage tools that this product's target user (a salesperson checking a queue) almost certainly already knows how to operate on sight.
Aesthetic-Usability Effect The card/badge/icon/motion system introduced in v1's F7 has been extended consistently as the app has grown — new surfaces (dashboard stat tiles, the topic template gallery, the source-precision panel) all read as the same product rather than bolted-on additions, and both the light and dark palettes were verified against WCAG AA contrast (v1, F8) rather than eyeballed.
Internationalization parity Every key in every English locale file has a corresponding German key and vice versa (checked file-by-file across all 8 namespaces) — there is no partially-translated screen anywhere in the app, which is a real discipline to maintain as a product keeps shipping new copy.
