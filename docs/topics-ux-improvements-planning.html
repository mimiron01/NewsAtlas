NewsAtlas — Topics UX Improvements Planning

Implementation plan for every gap raised in the topic-discovery UX audit: templates/AI-suggested topics, result-quality fixes, a per-topic feedback loop and analytics, onboarding, and management-UI parity with companies.

Status: Planning (2026-08-02). No code has been written for this doc yet.
Builds on: theme-search-planning.html (the original ThemeWatch/topic design this plan extends — read that first for the data model and ingestion pipeline this doc assumes), the topic/theme workflow-gaps session that shipped mute/pause/run-now/edit/dashboard-tile parity (commit 54c53ad) — this plan picks up from there, not from theme-search-planning.html's original v1 scope.
Primary users this plan optimizes for: non-technical business/marketing users creating topics to monitor industry trends relevant to their product (e.g. "Automotive", "EV Regulation"), not analysts who want boolean query languages.
Problem this plan is scoped against: two named pain points — (1) poor result quality (noisy/irrelevant matches, no way to tune a topic before or after creation) and (2) low discoverability (topics are a secondary, easy-to-miss feature with a blank-page creation flow). Every item below is justified against one or both.
Doc purpose: Turn the UX audit into a concrete, code-grounded spec an implementation session can work from directly. Every architectural fork is recorded as a decision; open items are proposed default (flag if wrong) or deferred to implementation.

2. Phase 1 — Query & UX foundations

No new tables. These make the existing create/edit flow honest and reversible before anything gets built on top of it.

Phase 1 Query & UX foundations

1.1 Fix "Themes" vs "topic" naming inconsistency frontend + i18n only

Current state: the nav (frontend/src/i18n/locales/en/nav.json:8) and the settings page heading call the feature "Themes", but nearly every piece of in-context copy on that same page calls it "topic" — e.g. themes.json:63 ("Topics can only fetch news via Google News RSS…"), themes.json:74-77 ("This topic is paused…"), SetupChecklist.tsx:34 (themeLinkLabel). A new user sees two different words for one feature within a single screen.

Decision — fix the user-facing word, not the codebase. Rename every user-visible string to "Topic"/"Topics" consistently. Do not rename the backend model (ThemeWatch), table (theme_watches/theme_matches/theme_follows), or API routes (/theme-watches, /theme-matches). Renaming those is a large, purely-cosmetic migration (table renames, every FK, every frontend API type, every test) with zero user-visible benefit — the user never sees a table name or a route path. Internal code keeping "theme" while the product word is "topic" is a normal and common split (see TargetCompany → "My companies" for the existing precedent of exactly this pattern in this codebase).

Change: i18n-only, no logic changes.

  • nav.json:8: "themes": "Themes" → "themes": "Topics" (key name stays themes to avoid touching every call site — only the value changes).
  • themes.json: every occurrence of "theme"/"Theme" in a user-facing string → "topic"/"Topic" ("Theme name" → "Topic name", "Tracked themes" → "Tracked topics", "Add theme watch" → "Add topic", toast strings, confirm-dialog copy, etc.). The strings that already say "topic" (the ones quoted above) are untouched.
  • SetupChecklist.tsx / common.json: themeLinkLabel copy → "Track a topic instead".
  • Page title (usePageTitle(t("themes:title"))) and the <h2> in ThemesPage.tsx:367 pick up the new themes:title value automatically once the i18n key changes — no component change needed.
  • Dashboard.tsx stat tile label (stats.newThemeMatches in the dashboard/common namespace) and panel heading (topThemeMatches) → "New topic matches" / "Top topic matches".

Acceptance criteria: grep the frontend for the literal word "Theme"/"theme" inside t("...") string literals and JSON i18n files (not variable/type/route names) and confirm zero remaining occurrences of the word applied to a user; German locale (de/themes.json etc.) updated to match ("Thema"/"Themen" → keep as-is only if "Thema" is already the correct German product word — flag for a native-speaker check, this doc doesn't assume it isn't).

1.2 Negative / exclude keywords backend + frontend + migration

Why this is the highest-leverage quality fix: query_terms is a flat OR list (build_theme_query, news_query.py:76-88) with no way to exclude anything, and unlike the company path, topics have no article_mentions_company grounding guard (news_query.py:98-116) — AI triage is the only filter. A non-technical user typing "Automotive" has no way to say "not insurance, not used-car retail" short of abandoning the term entirely.

TableColumnTypeNotes
theme_watchesexclude_termsARRAY(String), default []Same validation caps as query_terms (MAX_TERMS=20, MAX_TERM_LENGTH=100, reusing validate_term_list from common_validators.py). No minimum — unlike query_terms, zero exclusions is the common/default case.
# news_query.py — build_theme_query gains an optional exclude clause
def build_theme_query(
    query_terms: list[str], sources: list[str] | None = None,
    exclude_terms: list[str] | None = None,
) -> str:
    terms = _quote_terms(query_terms)
    base = " OR ".join(terms)
    if sources:
        site_clause = " OR ".join(f"site:{d.strip()}" for d in sources if d.strip())
        if site_clause:
            base = f"({base}) ({site_clause})"
    if exclude_terms:
        for term in _quote_terms(exclude_terms):
            base = f"{base} -{term}"
    return base

Google News RSS search supports bare -term exclusion the same way Google web search does, so this needs no new provider capability — just string composition. ThemeWatchCreate/ThemeWatchUpdate gain exclude_terms: list[str] = Field(default_factory=list, max_length=20) with the same validate_term_list validator as query_terms. ingestion.py's call to build_theme_query (around line 596) passes exclude_terms=theme_watch.exclude_terms.

Frontend: a second TagInput on the create/edit form, styled/labeled distinctly ("Exclude terms (optional)" with a red/muted tag style vs. the include list's default style, so the two lists are never visually confused). Reuses the exact component already used for query_terms/sourceAllowlist in ThemesPage.tsx:379-396.

Proposed default: also expose exclude-term suggestions reactively once §3.1's feedback loop exists (e.g. "you've dismissed 4 articles mentioning 'insurance' — add as an exclude term?") — not required for this item to ship, called out again in §4.1 of Phase 3.

Acceptance criteria: Alembic migration adds the column with server default '{}'; unit tests for build_theme_query covering exclude-terms-present/absent, combined with sources; existing topics with no exclude_terms produce byte-identical queries to today.

1.3 Query preview / dry-run before saving backend + frontend

Why: today a user sets query terms, saves, and only learns whether the query was too broad/narrow/dead at the next ingestion run (up to ingestion_interval_hours later, default 6h) or by clicking "Fetch now" and waiting. That's a blind, slow trial-and-error loop — exactly backwards for a non-technical user who doesn't think in search-query terms.

Decision — live Google News RSS query, not a stored/cached preview. The preview calls Google News RSS directly with the in-progress (unsaved) query terms/exclude-terms/sources, the same way GoogleNewsRSSClient.fetch_articles already does, and returns headlines without creating any ThemeMatch rows or running AI triage/summarization — this keeps the preview free (no Mistral cost) and instant, at the cost of not showing the AI relevance filter's effect. That tradeoff is fine: the preview's job is to catch "this query is obviously too broad/narrow", which raw headline volume already shows.

1.4 Duplicate-topic detection confirmation backend + frontend, small

Current state: get_or_create_theme (services/theme_follows.py:11-30) silently case-insensitively dedupes by name — creating "Automotive" when it already exists just follows the existing row and returns it, with no signal to the user that this happened. A user can end up following a topic with someone else's query terms/history and have no idea why it already has matches, or why editing "their" topic changes what other users see.

On a 409 with code: "duplicate_name", the frontend shows a dialog: "A topic named '{name}' already exists with these search terms: […]. Follow the existing one instead, or create a separate topic with a different name?" — "Follow existing" resubmits with confirm_merge: true (identical to today's silent behavior); "Rename and create separate" lets the user pick a different name and resubmits as a fresh create. Acceptance criteria: creating a topic with a genuinely new name is unaffected (no extra round-trip); creating one with an existing name (case-insensitive) always surfaces the choice, never silently merges.

2.3 AI-suggested topics, grounded in the curated template library backend + frontend

Why this is a small lift: workspace_settings.offering_description is already collected at onboarding and fed into every summarize_article/summarize_theme_article call (ai_client.py:504 etc.) — it is never used to propose anything today. This closes that gap with one new AI call, reusing the existing Mistral client wiring.

Decision — the AI helper is grounded in §2.1's template library, not a blank generator. A first draft of this item called Mistral with nothing but the offering description, generating every suggestion from scratch on every call. That's the wrong shape: it throws away the curation work §2.1 already did, can drift stylistically from the vetted templates (inconsistent naming, no exclude-terms discipline, no evidence the terms actually return good results), and gives an admin no way to improve suggestion quality except prompt-tuning. Instead, suggest_topics() is retrieval-augmented against topic_templates: fetch the full active template set (name, description, category, query_terms, exclude_terms — small enough to pass in full; no separate embedding/ranking step needed at this catalog size, revisit only if the library grows past what fits comfortably in the prompt), pass it to the model as labeled examples, and instruct it to do one of two things per suggestion: (a) recommend an existing template as-is or lightly personalized (e.g. add the workspace's own product terms to "Fintech & Payments"), which is the common case and inherits that template's already-curated exclude_terms and §2.4 track record, or (b) synthesize a new topic modeled on the same structure/quality bar only when nothing in the library fits the offering description well. This makes "the AI helper has example templates to draw from" literally true rather than aspirational, and gives every AI-personalized suggestion a plausible starting point that's already been through curation instead of being invented fresh each time.

4. Phase 3 — Feedback loop & analytics

Compounding quality improvements — most valuable after Phase 1/2 have been live long enough to generate real dismiss/status data. Extends a mechanism (ai_feedback_note) that already exists for companies but was never extended to topics.

Phase 3 Feedback loop & analytics

3.1 Per-topic feedback note backend only, small

The pattern already exists for companies — extend it, don't reinvent it. services/feedback.py's refresh_feedback_note computes a rule-based (no LLM call — pure SQL aggregation), workspace-wide note from dismissed-vs-reviewed Signal.signal_type patterns over a 30-day window, stored in workspace_settings.ai_feedback_note and injected into future summarization prompts (ingestion.py:947,1034). Topics currently get none of this — triage_theme_article/summarize_theme_article never reference ai_feedback_note at all.
TableColumnNotes
theme_watchesai_feedback_noteText, default "". Per-topic, not workspace-wide — a dismiss pattern on "Automotive" shouldn't bias "Series B Funding"'s prompts.
# services/feedback.py — new function alongside refresh_feedback_note, same shape
def refresh_theme_feedback_note(db: Session, theme_watch: ThemeWatch) -> None:
    """Same rule-based approach as refresh_feedback_note, scoped to one theme's own
    ThemeMatch history instead of workspace-wide Signal.signal_type."""
    since = datetime.now(timezone.utc) - timedelta(days=LOOKBACK_DAYS)
    rows = (
        db.query(ThemeMatch.extracted_company_name, func.count(ThemeMatch.id),
                  func.sum(case((ThemeMatch.status == SignalStatus.DISMISSED, 1), else_=0)))
        .filter(ThemeMatch.theme_watch_id == theme_watch.id, ThemeMatch.created_at >= since,
                ThemeMatch.status.in_([DISMISSED, REVIEWED, ARCHIVED]))
        .group_by(ThemeMatch.extracted_company_name)
        .all()
    )
    # same MIN_SAMPLE_SIZE / DISMISS_RATE_THRESHOLD gate as the company version

Called from the same place refresh_feedback_note already runs (end of an ingestion pass), once per active theme. triage_theme_article/summarize_theme_article (ai_client.py:455,500) gain an optional feedback_note: str = "" param, appended to their context lines exactly like the company path already does, and the two call sites in _process_new_theme_matches (ingestion.py:753,778) pass feedback_note=theme_watch.ai_feedback_note.

Proposed default: the note text focuses on what kind of content gets dismissed (using extracted_company_name patterns as a rough proxy, since topics have no signal_type-equivalent categorical field) rather than trying to infer semantic subtopics — flag if a richer signal (e.g. clustering dismissed articles' titles) is wanted; that's meaningfully more complex than the SQL-only approach this item is scoped to.

Frontend tie-in: surface the current note (read-only) on the topic's edit view — "Recent tuning: users have dismissed articles mentioning X; the AI is now stricter about these" — so the mechanism isn't invisible, and pairs naturally with §1.2's exclude-term suggestion idea (surface an "add as exclude term?" prompt when a pattern crosses the threshold).

Acceptance criteria: a topic with fewer than MIN_SAMPLE_SIZE dismissed/reviewed/archived matches produces an empty note (no premature bias from a handful of data points); existing topics' prompts are unaffected until they accumulate enough status history to produce a note.

5. Phase 4 — Discoverability & management parity

Makes the feature (and the templates built in Phase 2) actually findable, and closes the UI feature-parity gap vs. the company-tracking page.

Phase 4 Discoverability & parity

4.1 First-class onboarding step for topics frontend only

Current state: SetupChecklist.tsx:25-35 treats a topic as a secondary link inside the "track a company" step (secondaryTo: "/themes") — a new user has to already know topics exist to notice the link at all, despite the feature being pitched internally as the app's key differentiator ("industry-trend awareness, not just lead-finding" — theme-search-planning.html §1).

Decision — keep it inside the same checklist step (both still satisfy "something to fetch"), but make the topic path equally prominent, not secondary. Splitting into two separate checklist steps would force a user who only wants company tracking to see a step they'll never complete; instead, present both options with equal visual weight and let either satisfy the step, same underlying hasSomethingToFetch logic (Dashboard.tsx:171) as today.

Change: the "track a company or topic" step's body text presents two side-by-side actions instead of a primary link + secondary link: "Track a company" and "Browse topic templates" (linking into §2.2's gallery, not the blank Topics page) — same visual treatment, no primary/secondary hierarchy implied. secondaryTo`/`secondaryLinkLabel props on SetupChecklist get renamed to reflect this is a genuine either/or choice, not a fallback (e.g. altTo/altLinkLabel pointing at /themes?gallery=1 or similar deep link straight into the gallery).

Acceptance criteria: a user who only ever tracks companies sees no behavior change beyond the copy/link target; a user who lands on the gallery link from onboarding sees the template gallery first (not the blank create form) even before Phase 2's "default view for zero-topic workspaces" (§4.2) exists, since this is a direct deep link.

4.2 Empty-state template gallery on the Topics page itself frontend only

When themes.length === 0 (ThemesPage.tsx:423 currently renders a one-line "No theme watches yet." and otherwise shows the same blank create form as a workspace with 40 topics), replace that empty state with §2.2's template gallery front-and-center, collapsing the manual create form into a secondary "or create a custom topic" affordance below/beside it. Once at least one topic exists, the page reverts to today's layout (create form primary, list below) — the gallery stays reachable via the "Browse templates" entry point from §2.2, just no longer the forced first view.

Acceptance criteria: no backend change; purely conditional rendering keyed off the existing themes state already loaded by loadThemes().

A year-old decision made before any usage data existed; Phase 1-3 of this plan are exactly the kind of "reason to believe" that decision was waiting on, but this item still ships as strictly opt-in given no evidence yet either way.

4.4 Management-UI parity with companies frontend + backend (bulk endpoint)

Gap: SettingsTargets.tsx (companies) has a proper table layout, multi-select + bulk delete/unfollow (selectedIds state, handleBulkDelete, POST /target-companies/bulk-delete), and admin-only CSV import; ThemesPage.tsx's topic list (:487-556) is a flat <ul> with no selection, no bulk action, no search/filter/sort on the list itself (only the separate matches feed below it is filterable).

  • Bulk delete/unfollow: mirror target_companies.py's bulk-delete endpoint shape exactly — POST /theme-watches/bulk-delete { ids: UUID[] }, same admin-hard-deletes-vs-follower-unfollows branching already implemented per-topic in delete_theme_watch (theme_watches.py:155-176), just batched. Frontend reuses the exact selectedIds/checkbox/bulk-actions-bar pattern from SettingsTargets.tsx:34,193-209,286-312,324,388 — this is a near-mechanical port, not new design work.
  • Search/filter/sort on the topic list: a text filter (matches name/industry/query terms client-side, list sizes here are small — capped by max_active_theme_watches) and a sort control (by name, by §3.2's last_match_at, by created date) above the list.
  • CSV import: deferred — a company CSV row is one name + keywords; a topic CSV row would need query terms, exclude terms, and optional source/country/language columns, which is a heavier schema to get right and there's no evidence yet that bulk topic creation via spreadsheet is a real workflow the way bulk company lists are (sales teams commonly have a CSV of target accounts; "give me a spreadsheet of topics" is a less obvious existing artifact). Revisit if Phase 2's template gallery doesn't cover the bulk-setup need in practice.

Acceptance criteria: bulk-delete respects the same creator-or-admin edit gate as single delete (a non-admin's bulk request silently skips rows they don't own/follow rather than partially failing the whole batch — match whatever error-partitioning convention target_companies.py's bulk endpoint already uses, don't invent a new one).

6. Explicitly deferred (considered, not in this plan)

  • Unifying ThemeWatch/TargetCompany into one "tracked entity" concept with a type discriminator. This would remove the duplicated CRUD/permission/follow code between the two models and simplify the mental model long-term, but it's a breaking data-model migration touching every table, endpoint, and frontend type in both features — high risk, no user-facing benefit on its own (users don't experience the duplication as a problem the way they experience missing exclude-keywords or a blank template gallery). Revisit only if the two features' logic keeps drifting apart in ways that make maintenance genuinely painful, not for UX reasons.
  • Semantic/vector search for initial retrieval (today's embeddings are dedup-only, not used for matching/ranking). A real quality lever, but it's an ingestion-pipeline architecture change independent of everything in this plan, and Phase 1's exclude-terms + Phase 3's feedback loop should meaningfully close the quality gap first using the existing keyword-OR + AI-triage pipeline before adding a second retrieval mechanism on top of it.
  • Boolean query builder UI (AND/OR/NOT combinators, field scoping) — explicitly rejected for this audience. The user confirmed the primary persona is non-technical business/marketing users; a query builder serves analysts, and Phase 1's exclude-terms already covers the one boolean operator (NOT) that has a clear plain-language framing ("exclude"). AND/OR combinators stay implicit (terms are OR'd, exclusions are AND-NOT'd) rather than exposed as a builder.
  • Per-topic notification channels beyond the digest (Slack, SMS, push) — no evidence of demand yet and it's a different kind of integration work than anything else in this plan; the digest opt-in (§4.3) is the one additive-notification surface that reuses existing infrastructure.
